| 地图、TF、导航 | 原有算法和配置保留 | 正常转发，发送队列受限 |

深度预览采用间隔抽样而非跨边缘插值，保留被抽样位置的毫米数值，不把有损 JPEG 用于距离计算。深度 CameraInfo 随预览尺寸缩放；原始 CameraInfo 保留。

预览无观看者时不编码。单独的预览进程使用一个 OpenCV 线程，并以 nice 10 运行，使实际导航和识别先获得 CPU。查看图像本身仍有一定开销，不能宣称零开销。

## 关键实测

- Windows 本机的 WebSocket 订阅验证：原始布局的深度话题收到的是 **160×120** 的预览；树莓派本地同名话题仍为 **320×240**。证明重映射只作用于桥接服务。
- 深度图像载荷约 **30.84 Mbps → 0.87 Mbps**，降低约 97%。四路图像合计约 **35.78 Mbps → 1.14 Mbps**。这是应用载荷统计，不含 TCP/无线协议开销。
- 一个实际浏览器客户端保持连接时，无线发送流量采样约 **3.1 Mbps**，发送队列约 **1–3 KB**；此前有数 MB 发送积压。
- 新运行日志截至 20:00 没有 `outbox ... full`。
- 本地原始深度实测 **29.71 Hz**，320×240、16UC1；识别输出 **2.94 Hz**，人体推理中位数 **231 ms**、P95 **307 ms**（包含多话题诊断订阅时）。随后普通运行的日志常见 170–240 ms。不同负载数值不能视为同一场景的固定性能。
- 两个额外 Windows WebSocket 测试客户端同时订阅全部四路图像、地图和 TF，均持续收到地图、TF 和约 3 Hz 预览，没有发送队列满记录。
- 预览转换检查通过：JPEG 尺寸、深度尺寸、毫米值保留、输入字节不变、时间戳保留、无人观看时不编码、缩放内参。
- robot_base_bringup 定向构建通过；有原有 CMake 最低兼容版本弃用提示，没有构建错误。

## 时间戳与证据边界

Windows 与树莓派时钟相差约 **985 ms**；通过持久 SSH 连接测得，最短往返约 4.6 ms，时钟偏差估计误差约 ±2.3 ms。不能把跨机原始时间戳相减全部算成网络延迟。

校准后双客户端测试的深度到达年龄中位数约 62–64 ms、彩色约 88 ms、局部代价地图约 20 ms、全局代价地图约 37–40 ms。存在启动瞬间/单次调度抖动；保留地图的旧消息重放也会产生较大的最大年龄。人体标注图年龄还包含推理和预览限帧等待，中位数约 480 ms，不能与纯传输延迟混淆。

没有修改系统时钟，没有进行移动导航或真人跟随验收。人体检测日志仍偶有 `no valid depth`，这属于有效测距/场景条件问题，本次不以预览变快宣称测距或跟随已验收。

